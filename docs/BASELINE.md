# 基线与门槛（X01 / O9）

> V0α 出口门 1 的性能门槛：**萤火 v2.0.0（`8c4000c`）在本机的实测基线**，以及「门槛＝绝对线与基线×1.1 取较严者」算出的门槛表。
> 采样器是 `scripts/probe`（`node scripts/probe/run.mjs baseline`，见 §6）；基线原始结果存在 `scripts/probe/baselines/ff-v2.0.0.json`，集成者复测栖枝时用 `--compare` 对照。
> 采样时间 2026-10-24；规则与绝对线来自 `research/08-补充-3-roadmap-vs-daily-pain.md` §5.1（S1–S6）与 9-P9。

## 1. 结论（先看这里）

1. **萤火自己在 S2、S3、S5 的「绝对线」上就不达标**（S1 达标）。按既定规则（取较严者），门槛 ＝ 绝对线，V0α 必须**显著优于**萤火才能过：S2 进程树 privateBytes 300 MB（萤火 505 MB）、S3 打开 10,000 条消息的会话 ≤2 s（萤火 5.2 s，期间主线程整整卡 5 s）、渲染进程 ≤500 MB（萤火 681 MB）、长会话打字 P95 ≤200 ms（萤火每键 965 ms）。这正是 B2（尾部加载＋虚拟化）、B1（去星空、控制 GPU 层）要解决的东西。
2. **S1 的门槛实际是「基线×1.1」**：萤火总值 1017 ms（中位）→ **P75 ≤1125 ms、P95 ≤1126 ms**。但本机 Electron 自己的起步有强烈双峰（§4.1），环境噪声比 10% 大得多，所以探针**必须与基线同场交错测**（`--vs`）；更稳的口径是「应用自身增量」（总值 − 同场空 Electron）：萤火 108 ms，门槛 ≈119 ms。**请用户/集成者确认用哪个口径**（探针两个都报）。
3. **S2 的 300 MB 线低于「空 Electron 底噪＋萤火的 GPU 提交量」**：空 Electron 就有 163 MB（GPU 进程 93 MB），萤火的 GPU 进程单独 395–437 MB，而不含 GPU 的部分只有 109 MB。V0α 想过 300 MB，必须把 GPU 进程提交量砍到 ≈190 MB 以下（星空画布、壁纸纹理、`backdrop-filter` 层）。**需要决定：改口径（不含 GPU 进程 / 用私有工作集）还是保持原线**。
4. **S5 的单位要钉死**：O9 写的是 `percentCPUUsage`，Electron 在 Windows 上把它按 24 个逻辑核归一（已核对：我的单核口径 1.67% ↔ `getAppMetrics` 的 0.07%）。按这个口径萤火是 0.0696%，轻松低于 1%，原绝对线形同虚设，真正起约束作用的是「基线×1.1 ＝ 0.0766%（单核口径 1.84%）」。但 5 分钟内逐 30 秒读数的波动有 ±50%，10% 的容差在噪声之下——只能看多次测量的均值趋势。
5. **窗口不显示的探针有两处结构性偏差**（§3.1）：①隐藏窗口里页面仍认为自己 `visible`（`backgroundThrottling:false`），所以「页面隐藏即暂停」靠 `visibilitychange` 是**不会触发**的，B1 需要主进程在 `hide()` 时主动通知页面；**（集成者已做：`app:visibility` → `src/lib/windowVisibility.ts` 把它并进 `document.visibilityState`，原有的暂停逻辑不用改；探针模式不发这个事件，见 §8。）**②合成器不出帧，rAF 约 1.5 Hz，S5 对 rAF 驱动的装饰（星空、落雪）偏低，真实托盘状态要在集成包上人工复核一次。

## 2. 环境

- 机器：Intel Core Ultra 9 275HX，24 逻辑核，31 GB；Windows 11（10.0.26300）；**接电**；核显（Intel Graphics；独显未启用）；未核对 Defender 状态（Electron 启动双峰疑与之有关，见 §4.1）。
- 应用：萤火 v2.0.0 `8c4000c`（git worktree，复用本仓库 `node_modules` 里的 **Electron 45.0.0 / Chromium 156**——基线也跑在 45 上，所以对比里没有 Electron 版本差；萤火原本用 Electron 44）；基线 worktree 里只给 `electron/main.cjs` 加了两行「探针模式不显示窗口、不建托盘」的补丁（与栖枝底座的 `ALIGHT_PROBE` 行为一致），不改本仓库。
- 采样期间机器上还有其他程序在工作，整机 CPU 忙碌度在 S1 前后记录（`noisy` 标记）；S2/S5 的 5 分钟内整机 CPU 忙碌均值 13.1%。同一台机器上的重复测量见各节。

## 3. 方法

采样器是 `scripts/probe`（`node scripts/probe/run.mjs baseline`）。每次测量都用**全新的临时用户数据目录**（`--user-data-dir`，在临时目录下），`ALIGHT_PROBE=1` 让主进程不显示窗口、不建托盘；通过 `--remote-debugging-port` 用 CDP 驱动页面。每个配置目录里预置：一个把 Claude 配成「API 方式、地址指向本机」的最小偏好、一把假密钥（经 `safeStorage` 加密保存，不是真密钥）、可选的合成任务历史。**所有测量都不联网、不调用真实模型。**

### 3.1 无头（隐藏窗口）的取舍——先读这个

本轮约束是不弹任何可见窗口，所以窗口从不显示。实测这带来几个性质，影响怎么读数字：

| 事实（本机实测，Electron 45 / Chromium 156） | 影响 |
|---|---|
| 从不显示的窗口，`document.visibilityState` 仍是 `visible`（主进程设了 `backgroundThrottling: false`） | 「页面隐藏即暂停」的装饰动画不能靠 `visibilitychange` 自动验证；**S5 测到的是「窗口未显示」状态，不等于真实的托盘隐藏**——B1 要靠主进程在 `hide()` 时通知页面才可靠（见 §1 第 5 条） |
| 合成器不出帧：`requestAnimationFrame` 约 1.5 Hz；没有 `first-paint` / `first-contentful-paint` | **S1 不含首帧绘制**，量的是「DOM 里输入框可输入」；用 rAF 驱动的装饰（星空、落雪、蝴蝶）在探针里几乎不跑，S5 的 CPU 因此偏低 |
| `Page.captureScreenshot` 能工作（强制出一帧） | 截图可用 |
| 页面里 `setTimeout(0)` 在空闲时要 40–100 ms | 探针对「事件后回填」类判定做了轮询 |
| `PerformanceEventTiming` 要等呈现，隐藏窗口里取不到 | S4 / 打字延迟用「CDP 输入调用往返」代替（渲染进程处理完才应答），＝输入排队＋处理耗时，不含出帧 |

### 3.2 S1 冷启动到可输入

- **起点**：`spawn` 之前的 `Date.now()`（进程创建）。**终点**：页面里的探测器第一次看到主输入框「存在、非 `:disabled`、不在 `inert` 子树里、可见」——探测器用 MutationObserver ＋ 4 ms 定时器，时间戳是 `performance.timeOrigin + performance.now()`，与起点同一时钟。之后再用真实按键（`Input.insertText`）确认字真的进了输入框。
- 关开屏（`bootAnimation=false`）测。配置目录是「老用户」的：偏好已落盘，所以这是**进程冷启动**，不是 OS 文件缓存冷（没有管理员权限没法清缓存）；每轮之间等整机安静（CPU ≤12%，最多 25 s）。
- **同场交错**：基线与被测按 ABAB… 交替启动，另带一个**空 Electron 应用**（同样窗口参数）每轮一起测。原因见 §4.1：本机 Electron 自己的起步时间有强烈双峰，不交错就没法比。
- 三段拆分：**Electron 起步**（spawn → 页面导航起点，含主进程 JS 初始化）、**页面**（导航起点 → 可输入）、总计。主进程初始化耗时 ≈ 应用的「Electron 起步」− 空应用的「Electron 起步」。

### 3.3 S2 空闲内存

- 配置目录里放 1 个 200 条消息的闲聊会话；启动后首页静置，再用界面（Alt+2 → 点任务行）**打开这个会话**，静置 300 s，每 30 s 取一次进程树快照。读**最后 3 个样本的均值**（GPU 进程的提交量单个样本会抖 ±30 MB）。
- 内存口径 `privateBytes` ＝ 进程提交量（`PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`，PowerShell `PrivateMemorySize64`）。已用主进程调试端口调 `app.getAppMetrics()` 交叉核对：浏览器进程 38152 KB ↔ 38184 KB、渲染 / 网络进程差在抖动内，两者是同一个计数器，**与 O9 的定义一致**。另外给出**私有工作集**（`Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate`，任务管理器「活动专用工作集」，真正驻留 RAM 的非共享部分）和**不含 GPU 进程**的合计。

### 3.4 S3 长会话

- 合成数据：10,000 条消息的聊天任务（用户 / 助手交替，助手回复含列表与代码块，确定性伪随机数种子 9，逐字节可复现）＋ 1 个 200 条的任务，写成旧存储格式（`localStorage` 的 `<前缀>/v1`，约 1.9 MB）。栖枝的 B2 存储层会把这份旧数据一次性迁移进 SQLite，所以同一份种子对两个版本都有效。
- 三个量：①启动到主输入框可输入（带这份历史）；②**打开长会话到主线程安静**（点击后 1.2 s 内没有再出现卡顿）与打开时的最长连续忙碌；③打开后渲染进程 `privateBytes`；④在长会话底部输入框连打 30 个键，量每个 `keyDown` 的 CDP 往返（P95）。
- **局限**：旧格式存在 `localStorage`，受 5 MB 配额限制，而萤火保存时把单条工具输出截到 4,000 字符，所以「30% 消息带 >5 KB 工具输出」「≥240 MB 的导入会话」这两项在基线上**无法构造**；它们由栖枝的 B2 自己的 `check-store` 覆盖，探针在栖枝上通过 `store:` 通道另行补测（待 B2 的接口稳定）。「无响应」用「打开时连续忙碌 ≥5 s 或单键往返 ≥5 s」作风险判据（Chromium 对未应答输入事件约 15 s 才判卡死，这里取更严的 5 s）。

### 3.5 S5 后台 CPU

- 与 S2 同一次静置里采：相邻快照的进程 `TotalProcessorTime` 差 ÷ 墙钟间隔，去掉前 60 s 取均值，先得到**单核口径**（100 ＝ 吃满一个逻辑核）。O9 原定义用的是 Electron `percentCPUUsage`，它在 Windows 上按逻辑核数归一（＝占整机的百分比）：已用 `--wakeups`（经主进程调试端口调 `app.getAppMetrics()`）核对——单核 1.72% ↔ `percentCPUUsage` 0.06–0.09%，除以 24 核吻合。**判定用 `percentCPUUsage` 口径（占整机%），单核口径作参考**。窗口「未显示」≈ 最小化到托盘的状态（见 §3.1 的限制）。`idleWakeupsPerSecond` 在本机恒为 0（§4.3）。

### 3.6 这里没测的

- **S4**（输入延迟）：由 IME-10 给出，见 `docs/IME-CASES.md`（5 路并发流式输出下组合 / 按键 / 提交的 CDP 往返）。
- **S6**（独显不被唤醒）：本机目前只枚举到核显（`Win32_VideoController` 只有 Intel Graphics），独显处于关闭或 Eco 状态，测不出东西；需要独显开着时用 `Get-Counter '\GPU Engine(pid_<渲染进程 PID>*)\Utilization Percentage'` 按 LUID 汇总，人工做。并且不要长时间 GPU 压测（本机 ACPI 中断风暴）。
- **开屏下的首帧**：见 §3.1，隐藏窗口不出帧。

### 4.1 S1：Electron 起步的双峰

同一个 `electron.exe`、同样的参数，从 `spawn` 到调试端口可用（≈「Electron 起步」）本机多数是 **830–890 ms**，偶尔只要 **~130 ms**（约十分之一的启动；本次基线 7 轮里有 1 轮）。这不是应用的问题：空 Electron 应用同样如此；与整机 CPU 忙碌度没有可靠相关，启动前先让一个核转起来也不能消除（8 对对照：空闲 825–840 ms vs 预热 830–866 ms）。快速模式下萤火总值只有 ~280 ms，若拿它当基线，×1.1 的门槛只剩 ~308 ms、应用自身只能多花 28 ms——所以**单看总值、跨时间比较是不成立的**，必须同场交错（ABAB），并优先看「页面」与「增量」两列：萤火页面部分稳定在 145–150 ms（±5），主进程初始化比空 Electron 多 16 ms，应用自身增量 108 ms。

**开屏**：萤火开屏开着（`bootEnter: auto`）时，主输入框要等到开屏结束才可输入：**8.8 s**（整个应用 `inert`，键盘被开屏截获）。V0α 的要求是开屏期间下层应用已可输入，探针的 `smoke` 会检查（应用默认设置下 10 秒内主输入框可输入；栖枝上这一项是必过项）。

### 4.2 S2：GPU 进程是大头

进程树 privateBytes 504.8 MB 里，**GPU 进程 395 MB**（5 分钟内从 437 MB 缓慢回落到 395 MB，单个样本还会抖 ±30 MB），渲染进程 62 MB，主进程 36 MB，网络进程 11 MB。空 Electron 的 GPU 进程只有 93 MB——多出来的 ~300 MB 是萤火页面的 GPU 资源（星空画布、壁纸纹理、半透明玻璃层）。**不含 GPU 的合计 109 MB 非常稳定（±3 MB）**，而含 GPU 的合计在不同次测量间浮动 440–550 MB，所以对「含 GPU 的总值」做 ×1.1 的回归判定本身噪声就大于容差；渲染进程（62 MB）与不含 GPU 的合计才适合做回归门槛。

### 4.3 S5：CPU 几乎全在 GPU 进程

后台 CPU 单核口径均值 1.67%，其中 GPU 进程约 1.3%、渲染进程 ≤0.2%、主进程 ≈0.1%。空 Electron 是 0.35%。`getAppMetrics().cpu.idleWakeupsPerSecond` 在本机读数恒为 0（Windows 上该字段不提供有效值），所以 S5 里「唤醒次数」一项无法度量，只能看 CPU。

### 4.4 S3：每一项都不达标

10,000 条消息全部进 DOM（135,494 个节点），打开会话主线程连续卡死 **≈5.0 s**，渲染进程 **≈680 MB**，之后**每敲一个键都要重渲染整段会话**（CDP 往返 ≈965 ms／键）。「无响应」风险判据取 5 s，萤火刚好踩线（5.02–5.06 s）。启动本身不受影响（带这份历史启动到可输入 1046 ms，与无历史时 1017 ms 相当）——因为首页不渲染会话，问题出在打开会话那一刻。

| S3 | 「无响应」：打开时连续忙碌、单键往返均 <5 s | <5 s | 5.05 s | — | **<5 s** | **不过**（踩线） |
| S4 | 5 路并发流式下组合/按键/提交往返 P95 / P99（IME-10） | 100 / 200 ms | 2.5 / 3.3 ms | — | **100 / 200 ms** | 过 |
| S5 | 后台 CPU 合计（Electron percentCPUUsage 口径，占整机） | 1% | 0.0696% | 0.0766% | **0.0766%**（单核口径 1.84%） | 过 |
| S6 | 独显不被唤醒 | 0% | — | — | 人工 | 本机独显未启用，未测（§3.6） |

读法：「**不过**」的行表示萤火自己就超出门槛，V0α 要变绿必须实质性改进（不是「不比萤火差」）。「过」且门槛由基线×1.1 决定的行（S1、S2 渲染进程、S5）是**回归门槛**——V0α 不得比萤火差超过 10%（S1 同场交错、S5 看多次均值）。S3 的 ≥240 MB 导入会话与 >5 KB 工具输出两项无法在基线上构造（§3.4），由 B2 的 `check-store` 与探针经 `store:` 通道补测。

## 6. 复现

```powershell
# 1. 建基线应用（萤火 v2.0.0，git worktree；复用本仓库 node_modules；只改 worktree 里的 main.cjs 两行）
node scripts/probe/run.mjs ffbase                      # 打印目录，记为 <FF>
# 2. （只在要重新采基线时）测基线，约 20 分钟，期间别做重活；已有的基线结果在 scripts/probe/baselines/ff-v2.0.0.json
node scripts/probe/run.mjs baseline --app-dir <FF> --s1-boot --json out/baseline-ff.json
# 3. 测栖枝（先由集成者 vite build 出 dist/）并对照基线
node scripts/probe/run.mjs baseline --vs <FF> --compare scripts/probe/baselines/ff-v2.0.0.json --s1-boot --json out/baseline-alight.json
# 4. 渲染成 Markdown 表格
node scripts/probe/run.mjs report --json out/baseline-alight.json --md out/baseline-alight.md
# 5. 用完拆掉基线（会先拆 node_modules 目录联接，再 git worktree remove）
node scripts/probe/run.mjs ffbase --remove
```

`--quick` 是冒烟档（3 轮 / 40 s / 1 次），只验证流程，数字不能用。`--only s1,idle,s3,floor` 可只跑一部分。测量时**不要同时开别的重负载**（探针会记录整机 CPU 忙碌度，`noisy` 标记的轮次要重测）；本机用户在打游戏时不要跑。

## 7. 局限与待决事项

1. **S1 的原定义对环境太敏感**（§4.1）：建议门槛改成「同场交错下，应用自身增量 ≤ 基线增量 ×1.1，且总值 ≤ 绝对线」。探针两种都报。
2. **S2 的绝对线 300 MB 低于本机空 Electron 加 GPU 进程的底噪＋萤火的 GPU 提交量**（§4.2），按「取较严者」基线自己就不达标，V0α 想过线必须显著削 GPU 进程的提交量（星空、壁纸纹理、`backdrop-filter` 层）。需要决定是改口径（不含 GPU 进程 / 用私有工作集）还是把 V0α 的目标定为「显著低于基线」。
3. **S3 的 ≥240 MB 导入会话与 >5 KB 工具输出**在旧存储上无法构造（§3.4）。
4. 窗口不显示带来的偏差（§3.1）：S5 偏低（装饰动画不跑）、没有首帧。真实托盘状态下的 CPU 需要人工用任务管理器 / `getAppMetrics` 在集成包上复核一次。
5. 样本量：S1 每个变体 7 轮，P95 基本等于最大值；S3 只有 3 次。数字用来判断量级与回归，不是统计学意义上的精确分位数。

### 8.2 读这些数字的注意事项

1. **S3 与输入延迟必须用 `--osr`**。从不显示的窗口里合成器只有约 1 Hz 的节拍，页面一产生视觉更新，主线程就会在 `Commit` 里等下一次合成节拍——一次整整约 1,000 ms（用 Chromium tracing 抓到：长 `RunTask` 里只有一个 1,004 ms 的 `Commit`，JS 与布局都不耗时）。默认的隐藏窗口里，S3 打开长会话会出现 3 个这样的连续 1 s（「3,091 ms、P95 527 ms」），5 路并发的「工作」模式也会偶发——这些是窗口隐藏的假象，不是应用卡。`--osr` 让主进程在探针模式下改用离屏渲染 + 60 fps + 软件渲染（`ALIGHT_PROBE_OSR=1`，不碰独显），帧节拍正常后这些尖峰消失。S2/S5 不用 `--osr`（软件渲染没有 GPU 进程，内存数字不可比）。隐藏窗口下的 S3 原始数字：打开到安静 114 / 3,091 / 3,168 ms，打字 P95 2 / 527 / 2 ms，渲染进程 61–67 MB，DOM 790 个节点——只有最好的一次是应用本身的真实值。
2. **IME-10 在「闲聊」模式下测**：栖枝首页输入框默认「工作」（发出去的是制定计划的提示词，界面更重），而 5 路并发的用意是对话；`ime` 子命令发送前会先切到「闲聊」。「工作」模式在隐藏窗口里会偶发 §1 的 `Commit` 尖峰，不代表真实窗口。
3. **S1 的 +6% 是页面部分变重的结果**（≈ +65 ms：更大的组件树、更多样式、壁纸图层）；主进程初始化与萤火持平。门槛按总值 P75/P95 判，通过；按「应用自身增量」口径（§7 第 1 条）则偏高 49 ms，需要用户确认用哪个口径。
4. **种子的写法变了**：`prepareProfile` 现在在应用**第一次读库之前**（第一份文档、应用代码之前）把 localStorage 种子写好，让栖枝第一次启动就把旧格式任务迁进 SQLite；原先「先空启动一次再写种子」会让库里记下「没有旧数据」，种子任务永远不会被迁进去（探针看到的是空列表）。

### 8.3 S2 的现状与待决

- 夜景：含 GPU 的进程树 391 MB（GPU 进程约 292 MB）。集成时发现的大头是壁纸的低清占位层（整幅 `blur(26px)` 的滤镜表面，常驻在 GPU 进程里，占位用完也不会还回去）：**已删除**（本地图片几十毫秒就读完，占位没有意义），夜景 S2 由 460 MB 降到 391 MB（短测 440→330 MB）。
- 【2026-10-25 更新】①已处理：骨龙遮纱的元素缩成了四个遮罩椭圆的外接框（图坐标 x 359–1445、y 0–356，约整幅的 22%；遮罩在框外本来就全透明，所以画面不变——首页截图逐像素比较，最大差 2/255、5,730 个像素），转场 / 动画期间 GPU 负载大头就是它（夜转场 GPU 主线程占用 80% → 40%）。下面是处理前的记录。
- 还有两处明显的 GPU 开销，没动，因为动了会改画面，需要作者决定：①壁纸上的「骨龙遮纱」（`.wallpaper__dragveil`：`backdrop-filter: blur(5px)` + 4 个径向遮罩，整幅大小），实测约 50 MB；去掉 `backdrop-filter` 不省（遮罩表面还在），要省只能整个去掉或预烘焙进壁纸图；②夜景图的左缘羽化遮罩、各面板的 `backdrop-filter`：各约 25–100 MB，但同一个配置多次测量也会抖 ±30 MB（GPU 进程提交量的固有噪声），分不出单项。昼景 395–406 MB（GPU 约 300 MB），没有单个大头。
- 即使去掉遮纱（约 −50 MB），夜景也只到 ≈340 MB：**300 MB 的绝对线低于「空 Electron 163 MB ＋ 一幅全屏壁纸与玻璃层」的底噪**，与 §7 第 2 条同一个结论。需要用户决定：把门槛改成「不含 GPU 进程 ≤ 120 MB（现 100 MB）或渲染进程 ≤ 68 MB（现 55 MB）」，还是继续压 GPU 层（代价是改壁纸画面）。
