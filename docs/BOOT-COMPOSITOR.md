# 开屏 / 转场的合成器路径（comp）

用户在 240 Hz 屏上觉得转场「卡卡的」。原因有两层：

1. 开屏与转场里**由 JS 驱动**的画面（蝶、画布、标题、底板平移、拱窗……）被节拍器封顶在 60 fps（240 Hz 每 4 次刷新才画一次），而交给合成器的 WAAPI 元素每 4.17 ms 动一次——两种节拍混在一起；
2. 每个节拍都在改整屏大层的 `clip-path` / `mask` / `drop-shadow`，每拍整层重新光栅，解封 60 fps 之后 GPU 直接画不过来。

所以做法不是「把封顶去掉」，而是**让主要运动不再由 JS 逐帧驱动**：转场里所有视觉状态仍是转场时刻 `tr` 的纯函数（`trState` 与各场景 / 应用侧的纯函数），
新增的一层把这些函数**采样成 WAAPI 关键帧**交给合成器：每个刷新都出一帧，节奏由合成器保证，主线程不再每帧提交。

## 一条管线，两个出口

```
tr 的纯函数 ──► 通道 channels.ts ──► 采样器 sampler.ts ──► WAAPI 关键帧 ──► ClockGroup
                (native / poly)       原生缓动 / 折线 / 阶梯                   ├─ 实时：第一个 rAF 把 startTime 对齐到同一个 t0 后放手
                                                                              └─ 导出：__boot.seek(t) 把同一批动画的 currentTime 逐帧设一遍
```

- **native（原生缓动）**：`lerp(from, to, 缓动(win(tr, span)))`。缓动是 cubic-bezier（`bootMath.cubic` 的结果带 `.bezier` 四元组；`sstep` 恰好是 `cubic-bezier(1/3, 0, 2/3, 1)`），
  关键帧只要 2–4 个加同一条曲线，合成器自己算，零采样误差。
- **poly（折线）**：几何插值的缩放、飞行路径、拍翅、`dissolveFast`……按「误差 < 容限」（位置 0.25 px、不透明度 0.5/255，再乘安全系数 0.6）自适应二分采样，时间表段起止（`knots`）必取。
- **阶梯**：慢机器的退路。调速器升档后，通道改成 `steps(1, jump-end)` 的台阶，台阶长度 = 档位 × 刷新间隔，起点对齐 t0（`ClockGroup.retier`）。
- 向量的各分量就是 `css()` 里各个函数的参数；浏览器对「函数列表相同」的 `transform` 逐函数线性插值，所以在向量上线性插值与浏览器一致。
- `scripts/check-boot.ts` 对每条通道逐点对拍「关键帧求值 vs 纯函数」（`evalTrack` 在 node 里求值），所以实时、导出、legacy 三者一致。

## 合成器能做什么（实测，别越界）

能上：`transform` / `translate` / `scale` / `rotate` / `opacity` / 色彩矩阵类 `filter` / `backdrop-filter` / `clip-path` 的 `inset`（不带 round）、`polygon`、`circle`、`ellipse` / `steps()`。
不能上（`compositeFailed`）：`filter` 的 `drop-shadow` 与 `blur`、`clip-path: inset(round)`、`mask-position`、`background-position`、`letter-spacing`、`color`、`text-shadow`、`visibility`、`width`、`border-radius`。

推论：矩形硬边用「overflow:hidden 持有者 translateX(X) + 内层反向 translateX(−X)」，不用 clip-path；发光 / 字色 / 模糊用预烘焙层 + opacity 交叉淡化；逐字距用逐字 translateX。

## 调速器（governor.ts / pacer.ts）

不再有 60 fps 封顶。默认档位 divisor = 1（每次刷新都推进）。每个残余 JS 帧记主线程 CPU 时间，每个 rAF 记间隔（16 个一窗，互不重叠）：
p90 帧内 CPU > 0.5 × 刷新间隔，或 p90 rAF 间隔 > 1.5 × 刷新间隔，**连续两个窗口**都超线才升一档（1 → 2 → 4），升档后至少保持 600 ms，只升不降。
刷新间隔只往小了记（本次见过的最高刷新率）。开屏与转场的负载不同，转场开始时重新量（`beginTransition` 里 `carryOver()`：开屏里已经升到几档的，转场从一半起步；样本清空）。
转场开始的头 `QUIET_MS`（150 ms）不评估（样本丢掉）：起步那几帧（创建动画、首次光栅）的卡顿是起步本身的事，不是「这台机器画不动」；以前它会让头两个窗口都超线、转场一开始（约 +60 ms）就升到 2 档。
开屏里同理：预热（`warm.ts`，开屏播到约 0.9 s）把探针放上去 / 撤下来、偷看应用时 Viz 要现编着色器，rAF 间隔会拉长一两个窗口，但那时 GPU 只有 30–45% 忙——夜开屏 5 轮里有 5 轮恰好在这里（页面时间 1.6–2.6 s）被升到 2 档，之后一直 120 Hz（开屏内容更新率 148 Hz）。
`warmBoot` 现在调 `bootGovernor.quietFor(WARM_QUIET_MS = 1500)`：预热窗口里不评估，过了这段持续吃紧照样升。
**rAF 间隔拉长而帧内 CPU 很小 = GPU 背压，这时升档是对的，别把它当「误判」去掉**：档位升到 2 之后所有动画一起走阶梯（`steps(1, jump-end)`，台阶 = 2 个刷新间隔），没有变化的刷新不产生有内容的合成帧，GPU 的活几乎减半
（实测夜 / 昼快速版：不升档时转场头 300 ms GPU 线程 100% 忙、出帧 60–100 fps；升档后约 45% 忙）。曾经试过「帧内 CPU < 0.15 × 刷新间隔就不升」，快速版直接退步（夜 187 → 146 fps、昼 183 → 145 fps），已撤回。
独显才把下限设成 `refresh/60` 取整（种类来源：设置 › 外观 › 图形处理器问到的真实结果连同当时的启动偏好记在 `localStorage['alight.gpuKind']`（`'<atLaunch>:<kind>'`）；开屏时再问主进程「这次启动用的偏好」`desktop.app.gpu(true)` 核对——轻量，不收集 GPU 信息，开屏期间不能跑 `'complete'`；偏好变了或没有记录就按偏好算，`high` = 独显）——那是对本机「独显持续 3D 负载触发 ACPI 中断风暴」的保护，不是通用上限。
昼的**转场**用调速器（`bootImpl.ts` 的 `GOVERNED_TR`：窗 / 立绘 / 底板 / 轮廓 / 蝶全在合成器上，残余 JS 只剩标题 / 枝 / 光尘小块）；昼的**开屏**自 0.1.4 起也用调速器（`GOVERNED` 里有 `'day'`），并把节拍**锁在约 120 次/秒**（`LOCK_HZ`，见文末「第六轮」）：
0.1.3 的昼开屏每拍写 `mask-image`（绽开的径向蒙版并集）、每拍重光栅整屏三层，合成器画不了，解封只多出一点内容更新率（67 → 74 Hz），所以当时留着 60 fps 匀速封顶；0.1.4 把这些每拍重光栅的东西拆成画布 / 位图 / 合成器层之后才解封。

## 夜转场里谁在合成器上

| 元素 | 做法 |
| --- | --- |
| 底板的「洞」 | `.boot__hole`（overflow:hidden）`translateX(X)` + `.boot__plate-body` `translateX(−X)`，X = max(左栏宽, 取景平移露出的暗带) · PAN_E(pan)，与左栏面板推入同曲线同起点 |
| 底图（canvas.boot__bg） | 定格：`translateX`；被打断：`translate · scale` 仿射（plateFit）；都是 PAN_E 原生缓动，不再每拍重画 |
| 底板溶解、暗纱三层、前景画布与小件淡出、署名、首页壁纸层（individual `translate` / `scale`） | native / poly 通道 |
| 蝶 | 三张位图层（柔光、本体、翅面高光；`plus-lighter` 叠加，放进 `isolation:isolate` 的小组）+ 小组的位姿折线（约 60–100 关键帧）；光尘是只盖路径外接框的小画布，每个节拍重画 |
| 标题组（栖枝 / ALIGHT） | 已完全浮现时换成预烘焙叠层：光晕层（透明字 + text-shadow）/ 渐变字层 / 纯字标色字层，整体位姿折线、逐字 translateX 收拢字距、两层 opacity = tint；还在浮现中（被打断得早）退回 JS 逐拍写 |
| 左栏底色光晕 | `.side-nav::after`（z-index −1 的薰衣草色块）的 opacity；不再逐拍 seek `background-color` |
| 品牌标「亮一次」（夜、昼） | 品牌标的一份克隆 + 静态 `drop-shadow` 光晕（8 px / 18 px 两层），只动 opacity（不再动画 `filter`）。注意：旧实现的「峰值」字符串替换把偏移写成了 12 px（光晕偏向右边），这里取的是居中的光晕 |
| FlowerSea | 外包一个 div 作为「行」，动画挂在 div 上（svg 根元素上的动画合成器画不了） |

残余 JS（每个节拍按调速器档位写）：被打断得早的标题、枝的描画（SVG，同值去重）、光尘小画布。

## 昼转场里谁在合成器上（花海收进窗）

通道定义在 `dayComp.ts`（纯函数，`dayGeom` 缓存窗的几何：`at(tr)` = trState + archClip + 裁切矩形 + 镜头），DOM 与动画在 `dayTrComp.ts`（`prepareDayTransitionComp`，`dayScene.prepareTransition` 在 comp 下转给它；legacy 路径原样保留）。

| 元素 | 做法 |
| --- | --- |
| 窗（花海收进拱窗） | `.bd-bloom` 的 `clip-path: polygon()` WAAPI：64 个顶点（上两角各 24 段圆弧、下两角各 6 段），一条折线通道；外接框 = `archClip` 的裁切矩形（check-boot 逐点对拍）。合成器把 polygon 当成「画一张遮罩层」每帧重画（面积正比），这是窗本身不可省的一份 |
| 立绘与分身 | 原画 / 分身 `img` 的 translate（原生缓动 ART_E）+ scale（折线）、不透明度（native / poly），各自是合成层 |
| 窗左缘的软边 | `.boot__sveil`：窗左缘下面那些东西（壁纸色 + 底色层 + 底图位图，后两层各按 1 − bg 淡出，与下面真的底板同一个式子）的一份拷贝，静态渐变遮罩（不透明 → 透明，宽 `VEIL_W` = 90 个舞台单位），随窗左缘 `translateX`，**整条按软边宽度 `scaleX`**（遮罩跟着缩放：窗里的内容从左缘起 fw 宽渐显，与 legacy `mask-image: linear-gradient(90deg, transparent l, #000 l + fw)` 同一条渐变），内层 `scaleX(1/s) translateX(−l)` 钉回屏幕；不透明度 = sstep(fw / 16)。第二轮的版本只按 fw 缩放不透明度（左缘处的覆盖只有 fw / 90，软边读成一根硬竖条），已改 |
| 底板 | `plateBake.ts` 把「渐变底图 + 模糊光晕 + 三角纹 + 顶沿菱形 + 柔光」烘成一张**不带底色**的位图（按 CSS 像素烘；绽开结束 2.75 s 后空闲时烘好，导出模式转场起步时现烘）；底色（`#d4c8e4`）是它下面单独的一层纯色（主体里就是原来的 `.boot__plate`）。**两层各按 1 − bg 淡出**（legacy 是底色层 / 底图层 / 柔光层各按 1 − bg 淡出，叠起来颜色 = (1 − bg)·底图 + bg(1 − bg)·底色 + bg²·下面的东西；烘成一张带底色的位图再按 1 − bg² 淡出会偏亮偏灰 bg(1 − bg)·(底图 − 底色)，最大约 7 级）。主体 / 斜坡 / 左边一条是三个 `overflow:hidden` 持有者（补集 = 「窄遮罩斜坡 + 实心主体」）`translateX` + 内层反向 `translateX`；斜坡 = 底图位图（静态渐变遮罩 0 → 1）+ 它下面一条同样 0 → 1 的底色渐变（legacy 里底色层与底图层各被同一条补集遮罩羽化一次）。纸面不再逐拍 seek `mask-position`（`dayEntrance.main` 有窗时直接返回；开屏很早被打断、没有窗时仍是 legacy 的按时间推进的展卷遮罩）。**纸面一直在，前缘右边与羽化带里由「壁纸色擦除层」把它擦掉**（`.boot__wall`：纸面范围 [主栏左缘, 右缘 + 64] 里的一个静态 overflow 持有者，里面一块 0 → 1 渐变到壁纸色的元素随前缘 `translateX`；在底板下面、应用上面；壁纸色 `WALL_RGB` 是纸面下面那块壁纸的均值，竖向只在 ±5 级内变）——legacy 里那里是纸面被前缘遮罩、露出壁纸，底板在 bg 淡出时透出来的是壁纸而不是纸面；快速版里 bg 在窗左缘到位之前就开始淡了，不擦的话纸面的右缘（带圆角）会从底板里透出来 |
| 窗里的临时件 | archBg / archFog / archDeco / archFlw：opacity / translate；**晚建**（`Stager` 按它们第一次看得见的时刻），起步头几帧只建窗 / 立绘 / 主体底板 |
| 窗的轮廓 | 白框与描边拆成小件：四条直边（长条 `transform` 摆位 + `scale` 定长）、上两角与描边的下两角是小画布（每个节拍按半径重画，位置 / 不透明度走合成器；左上角的画布里再按 legacy 的轮廓遮罩画一条左缘渐变 aL → 1（宽 190 个舞台单位），不能整件乘 aL——弧延伸到窗里几百个单位，高速段整条上弧会消失）、白框的下角是固定半径的带边框小件（只平移）、窗台是持有者 + 内层条（持有者本身不透明，淡入淡出在内层条上；第二轮的版本持有者带着 `.dfp` 缺省的 opacity:0、没人动画它，窗台整条看不见，要到 wOut 交接真拱窗自己的窗台才冒出来）。窗宽 < 屏宽 85% 才看得见，所以也晚建 |
| 落影 | 静态的「终态拱窗」落影（窗收到位时自然露出）+ 左缘竖向软阴影条（随窗左缘平移） |
| 蝶 | HTML `div` 外包（位姿 / 左右翅 / 足），里面是小 SVG——SVG 根元素上的动画合成器画不了 |
| 标题组 | 已完全浮现时换成预烘焙叠层（光晕 / 渐变字 / 纯色字，逐字 `translateX`）；整体淡出折进各层不透明度（少一个渲染面）；还在浮现中（被打断得早）退回 JS 逐拍写 |
| 雪点 / 品牌标光晕 | 每粒雪各自 opacity（整层 opacity 会让 2400 × 1500 的层成渲染面）；品牌标光晕 = 克隆 + opacity |

起步：同步段 ≤ 8 ms（实测 5–9 ms）。`warm.ts` 在开屏播到约 0.9 s 时放几块小探针（polygon 动画、带遮罩的持有者、opacity 组里的 blur）把第一次用时要现编的着色器先跑掉，
并让开屏舞台（`.boot__stage`）暂时变成 99.8% 不透明度的渲染通道 5 个 rAF（`peekApp`）——开屏底板不透明，Viz 把它下面的应用整个剔掉，应用里的玻璃 / 阴影 / 渐变着色器要等转场第一帧才第一次现编
（实测起步 300 ms 内 `GrShaderCache::store` 约 20 次、`FinishPaintRenderPass` 97 ms，最长一个出帧间隔 72 ms；偷看之后 57 ms / 46 ms）。

## 昼开屏

开屏里的瓦片光栅（实测 7 s 里 3.3 s，GPU 主线程占用 80%）主要来自三处，都已处理：

- **枝的烘焙**（`dayScene.bakeTwig`）：枝的主体（填充 + 两个 `feDropShadow` + 描边 + 白帽）是静止的，每拍变的只是显现用的遮罩（7 条描边的 dashoffset），SVG 每拍要把整根枝连同滤镜在一个 3300 × 2400 的图层里重新栅格。
  现在主体烘成一张位图，每拍只在一张小画布里画 7 条带虚线的描边当遮罩、`destination-in` 一下（`pathLength = 1` / `dasharray 1 3` / `dashoffset 1 − p` ⇒ 路径起点起长度 p 的一段，round 帽，线宽 30，与 SVG 的遮罩同义）。
  只在 comp + 实时里做；导出模式（`__boot.seek`）与位图没好 / 失败时仍走 SVG（地址里加 `?twigbake` 可在导出里也开，对拍用；枝的位图对拍：平均差 0.05 灰阶、> 48 灰阶的像素 0.02%，全是边缘抗锯齿）。
- **合成层提升**：开屏里 JS 每拍写 `transform` / `opacity` 的层（`.bd-near1/.bd-near2/.bd-bfzoom`、雪点 `.bd-snow > i`）加 `will-change`，位置 / 缩放由合成器画，不再整层重新栅格（`.bd-world` 原本就有）。
- 偷看预热（见上）把应用的着色器编译挪到开屏里。

## 起步

`beginTransition(scene, kind, from, { live: true })`：同步段只量目标位置、建场景里马上要动的几个动画；应用侧入场的量取与其余动画由 `Stager` 按 deadline（最晚什么时候必须存在）排队，在后续的节拍帧里限额创建（导出模式不用，全部立刻建）。
开屏播到约 0.9 s 后 `warm.ts` 把暗纱 / 颗粒与应用侧入场目标先升成合成层（只在 `html[data-boot="on"]` 内生效），转场第一帧不必再等一次整屏光栅。

**起步 80 ms 里主线程在干什么**（`tp()` 给 `Stager` 的每个任务打点：`job@deadline:毫秒:名字`，在测量台结果的 `prof` 里）：昼完整版起步的 80 ms 里任务合计约 54 ms——窗的裁切折线采样 8、蝶的四条通道 5、底板拷贝画布 + 斜坡 / 薄纱 7、应用侧入场的采样 / 量取 / 建动画 5、窗的轮廓 11、落影 / 窗里的临时件 / 标题各 3–4。老做法是「deadline ≤ tr + LEAD 的不看预算」，起步头几帧里都是到点的，于是挤成一个 15 ms 的定时器任务 + 一个 13 ms 的 rAF 任务（起步 150 ms 里最长的 rAF 间隔 29 ms）。现在：
- `Stager.pump` 按预算（每帧约 2.5 ms，至少建一个）建，**只有过期（deadline + `GRACE` = 20 ms ≤ tr）的才不看预算**；deadline = 第一次变化 − `LEAD`（30 ms），所以起点就要在的那一批（蝶……）在头 20 ms 里一帧几个地建，其余的在预算里提前建、最迟在第一次变化前 10 ms 建完；
- 折线通道（`samplePolyGen`）分段采样：每采完时间表里一小段（≤ 40 ms 的跨度）让出一次，`ClockGroup.animate` 的任务每块最多占 1.5 ms（`SAMPLE_SLICE_MS`），采完才 `animate()`（任务返回 `false` = 没做完，`Stager` 把它排回去）；
- 窗的裁切 `winClip` 声明 `start: S.win[0]`（窗在那之前就是整个盒子，p = 0 的多边形 = 整个矩形），不再是「起点就要」的一员；
- 窗的轮廓（11 ms）拆成几个任务：画布件的 DOM 与它们的动画在同一个任务里（JS 马上就要每个节拍往里画），直边条 / 窗台 / 落影各自一个任务。**晚建件的动画必须 `sync`（与它的 DOM 同一个任务）**：试过把它们改成各自排队、与 DOM 错开几帧，昼快速版转场头 300 ms 里 GPU 画布命令从 37 ms 涨到 260 ms（出帧 189 → 145 fps），原因没查透（JS 每个节拍往画布里画、而画布件的合成器动画还没建？），但结论明确；
- 应用侧入场里署名在被藏起来（`visibility:hidden`）的真拱窗里：它的 opacity 动画在拱窗露出来（`creditIn` 起）之后再建（`hold(…, late)`：`notBefore`），否则 Chromium 判成「没有可见变化」、合成器画不了（昼的 `compositeFailed` 1 → 0）。

结果（昼 auto / fast，测量台 5 轮中位数）：起步 150 ms 内最长的 rAF 间隔 25–33 → 16.7–20.8 ms，最长的 Viz 出帧间隔 24–35 → 11–13 ms，长任务（> 16.7 ms）1–2 → 0，LoAF 0。

## 单帧 GPU 代价的结构（昼，冻结帧基准）

逐场景 A/B 的单次转场只有 1.2 s、瞬态里什么都在动，噪声大、也分不清「哪个元素占多少」。所以做了一个**冻结帧基准**（`perf-work/r2tools/frozen.mjs`，见 `perf-work/harness/README.md`）：
开发服务器页面里用 `__boot.seek` 把转场冻在某个 tr，叠一层整屏、几乎透明、opacity 动画的驱动层逼 Viz 每个刷新整屏重画，量稳态的 Viz fps 与「单帧代价」（GPU 线程忙 ÷ 帧数），CSS / JS 变体在同一个 Electron 里交错。得到的结构（昼完整版，2 轮中位数，单帧 ms；4.17 ms 是 240 Hz 的线）：

| 冻结在 | 0.5 s | 0.6 s | 0.7 s | 0.8 s | 0.9 s |
| --- | --- | --- | --- | --- | --- |
| 整体（r1 终版） | 0.8 | 3.6 | 4.4 | 4.1 | 1.7 |
| 整体（第二轮终版） | 0.7 | 1.3 | 2.9 | 3.2 | 1.4 |
| 只留应用（藏起整个开屏层） | 0.7 | 1.3 | 1.6 | 2.1 | 1.5 |
| 只留开屏层（藏起整个应用） | 0.7 | 0.8 | 1.1 | 1.2 | 0.6 |

- **0.6–0.8 s 整体在 3.5–4.4 ms，贴着 4.17 ms 的线**：应用 1.3–2.1 + 开屏层 2–2.8，没有余量——离屏测量台里 Present 的长停顿就出在这一段。
- **应用侧的大头是 `backdrop-filter`**：把应用里全部 BF 关掉，0.75 s 的单帧从 3.2 降到 1.7（−1.5 ms）。其中**BF 在「半透明淡入的块」里最贵**（0.75 s 的应用侧 3.2 → 去掉块里的 BF 2.1、去掉主栏玻璃 1.9、去掉控制台条 2.8）；同一批 BF 在终态（0.9 s 以后）只占约 0.5 ms。
  微基准（`proto-compositor/lcost.htm`）：一块 BF 约 0.1–0.35 ms（小的在下限、整列大的在上限），模糊半径、有没有 saturate 基本不影响（`blur(1px)` / 只留 `saturate()` 与 `blur(12px)` 一样贵）——代价是「多开一个渲染通道、读一次背板」，不是模糊的运算量；一个整屏的半透明渐变 / 图片层 ≲ 0.05 ms、一个不透明度组 ≈ 0.1 ms。所以别拿「面积」估成本，要数 BF / 渲染通道 / 遮罩的个数。
- **开屏层的 2–2.8 ms 是很多块各占一点**：整个窗（`.bd-bloom`）−1.7–2.1；窗的落影 + 轮廓 + 左缘落影合起来 −1.5–2（各自单独只有 −0.2–0.9）；底板位图与斜坡 / 薄纱 −0.4–1.4；窗里的底色（`archbg` ×2）、立绘（`s0-art`、`boot__fig`）各 −0.4–1.1；
  旧的开屏层（近景 / 枝 / 前景画布）−0.1–0.6，小件（尘 / 标题 / 蝶）≲ 0.3。**单项消融不可加**：忙度在饱和时被背压撑大，只能看「去掉这一项之后有没有跨过 4.17 ms 的线」；去掉落影 + 轮廓整组就从 3.1 降到 1.4（0.6 s）、4.5 降到 2.3（0.7 s），每一项单独去掉都不够。
- 已经确认**不贵**的：零不透明度、但仍挂着动画的层（视觉上已淡出的近景 / 枝 / 画布 / 底板位图 / 立绘……）——在 0.48 s 起把它们 `visibility:hidden` / `display:none`，Viz 出帧、GPU 忙度都没有变化（Viz 不画 opacity = 0 的 quad）；去掉 `.s0-art` 的 `mask-image`（少一个遮罩渲染面）也没变化；
  动画走完后的「平尾巴」（`fill: both` 的动画还在 tick）只在 1.0 s 以后多占 GPU 约 10–30 个百分点，但那一段本来就 240 fps。
- **阶梯（`steps()`）对 GPU 吃紧的情形是有效的**：快速版转场头 300 ms，调速器升到 2 档后 GPU 线程 45% 忙、240 fps，不升档则 100% 忙、60–100 fps。但昼完整版 0.6–0.9 s 里升不升档都没有太大差别（冻结基准里单帧代价本身 > 4 ms，阶梯只是让帧稀一点）。

这一轮据此做的：转场期间关掉内容列里的 BF（块是 backdrop root，BF 在块里没有效果）；昼关掉主栏玻璃的 BF（糊前糊后只差蝶纹的锐度）；昼的底板位图 `alpha:false`（合成器能把下面的应用剔掉）。没动的：夜的主栏玻璃（糊的是壁纸）、控制台条、左栏。

## 第三轮：对一块空白开着的 filter（夜 fast 与夜开屏的大头）

第二轮收尾时夜 fast 仍是 185–198 fps、p95 9–14 ms，LoAF 3/5 轮，夜开屏被调速器在约 2.9 s 升到 2 档。前一位修复者在 BF（左栏 / 主栏玻璃 / 控制台条）上花了很多力气（去遮罩、去圆角、换模糊半径、把骨龙遮纱与壁纸左缘的遮罩烘成位图），
这些各自只有几个 fps；真正的大头是别处：

**「栖枝」的 `h1` 上有三层 `filter: drop-shadow()`（24 px / 34 px 的大模糊）。它在开屏 5.6 s 字开始浮现之前、以及转场里「不带着走」的标题（快速版在 3 s 打断，字还没出来）那段时间，里面的字全是透明的——
可 `filter` 不看内容：合成器每一帧都给这块 759 × 137（再加 3σ 外溢）的空白开一个渲染通道、跑三遍大模糊。** 冻结帧基准里这一项单独占 2–4 ms，整个夜开屏前 5.6 s、整个夜 fast 转场都背着它。
排查路径：冻结帧（夜 fast，tr = 0.5）把 `.boot__title` 整个 `visibility:hidden` → 119 → 233 fps，而它里面的 sweep / `.boot__tt` / text-shadow / 混合模式单独关掉都没有变化；那就是 `h1` 自己的 filter。
`perf-work/r2tools/scan.mjs` 可以直接列出「带 filter / BF / mask / clip-path 的元素」和它们此刻的有效不透明度、内容不透明度（`eff` / `kids`）——`eff = 1 且 kids = 0` 就是这种空白通道。

修法（nightScene.ts，只在 comp；画面逐像素不变——全透明的内容投不出影子）：
- 开屏：`renderDom` 里 `t < T0`（5.6 s，「栖」开始浮现）把 `h1.style.filter` 设成 `'none'`，浮现的第一拍还给样式表里那一条；
- 转场：不带着走的标题（`!fh1`），字的此刻不透明度 `chBase.op × (1 − ambient)` > 1/255 时保持样式表里的 filter，淡到不可见就关；带着走的（`fh1`）仍是 `tintGlow(tint)`；完全浮现的走预烘焙叠层（`h1` 被 `visibility:hidden`，本来就没有这个通道）。

实测（离屏测量台，交错 A/B，4–5 轮中位数；r3a = 第二轮收尾 + 上一位修复者未完成的壁纸遮罩 / 骨龙遮纱烘焙，r4a = 再加这一条）：

## 第四轮：审美评审的视觉回退（昼的窗台 / 软边、夜的品牌标光晕、夜被打断的标题高光）

评审用 headless Chrome 软件渲染对 9522fbf 与第三轮终版逐帧对拍（`perf-work/parity`，夜 / 昼 × 完整 / 快速各 24 帧、打断点 3.0 / 6.8 s 各 12 帧）。四条 high、两条 medium，根因：

| 现象 | 根因 | 修法 |

## 第五轮：代码复审与审美复评的修复

代码复审（读码 + 真应用屏幕投射实测）核实了两条，审美复评核实了一条 high、五条 medium。修了下面这些；没修的写在最后。

### 代码

- **转场收尾闪一帧开屏画面（high，夜 / 昼 × 完整 / 快速 / 点击都有；回归）。** `finish()` 先 `r.end()`、再 `done()`（只是 `setBooting(false)`，React 要到下一个宏任务才卸载开屏层）。
  comp 路径的 `sceneTr.end()` 是 `group.end()`——把场景 `ClockGroup` 里**所有** `fill: both` 的动画都 `cancel` 了，包括覆盖层里的（底板溶解、洞、暗纱、前景、标题叠层、蝶；昼的窗、立绘、底板拷贝）。
  覆盖层的终态（透明 / 移出）只靠这些动画的 fill 保持，一撤就瞬间回到完整不透明的开屏定格画面，在卸载之前被画出一帧（60 Hz 约 17 ms）。legacy 靠内联样式停在终态，没有这个问题；`SceneTransition.end` 的契约（bootTypes.ts）本来就写的是「只撤挂在应用元素上的动画，覆盖层内部的随卸载」，实现与契约不符。
  修法：`ClockGroup.animate` 加 `app` 选项（夜：首页壁纸层 `.wallpaper__frame` 上的 backdrop 动画；昼没有），新增 `ClockGroup.release()` 只撤 app 的；两个场景的 `end()` 改成 `release()`，`dispose()`（导出模式往回 seek）仍 `end()` 全撤。
  DOM 采样（rAF / setInterval）看不到这一帧（取消与卸载之间的那一帧在两个 rAF 之间被画出），所以回归检查用屏幕投射：`tr-probe.mjs --osr` 新增 `night-flash` / `day-flash` 两个场景，用 `Page.startScreencast` 的小图逐帧与定格开屏帧比，转场明显离开开屏（差 > 15）之后不许再有一帧回到开屏（差 < 5）。
  修前的构建（final-app）两个场景都失败（夜：#43 #44 两帧差 0.3；昼：#33 一帧差 0.3），修后（fix-r7-app）通过（最小差 夜 21.9 / 昼 28.7，最后一帧与首页差 0）。
- **调速器 `carryOver()` 把刷新间隔清掉，独显的保护档对转场从不生效（medium，回归）。** `beginTransition` 先 `carryOver()`（里面 `reset()` 把 `refresh` 清成 undefined）再 `scene.prepareTransition`，而 `floorDivisor` 要有 `refresh` 才不是 1；
  夜 / 昼场景在 `prepareTransition` 里读到的恒是 1，独显（240 Hz）上整段转场的合成器通道按 divisor = 1 采成平滑关键帧，之后 `refresh` 重新量到时也没有 retier 触发。
  修法：`carryOver()` 把见过的刷新间隔存进 `carried`，`floorDivisor` 取 `min(refresh, carried)`；`reset()`（新的一次开屏）才清。**没有**把 `refresh` 本身带进转场：第一版修法（`carryOver` 保留 `refresh`）实测会让集显的升档判据变紧——
  转场里被 GPU 背压拖到每两个刷新一帧时，重新量的刷新间隔读成 120 Hz、阈值随之放宽、停在 2 档；带着开屏里的 240 Hz 进来，同样的背压一路升到 4 档（60 次/秒的台阶）：昼完整版 3 轮里 3 轮到 4 档（原来 1 轮）。所以升档判据仍在转场里重新量，保护档才用带进来的值。
  check-boot 补了用例：独显 240 Hz `carryOver()` 之后 `floorDivisor` = 4、`refreshMs` 仍是 undefined、之后量到 120 Hz 保护档仍是 4、再 `carryOver()` 仍记着、`reset()` 清掉、集显不受影响；`carryOver()` 在源码里先于 `scene.prepareTransition`。

### 画面

- **昼窗台左缘渐隐（high）。** legacy 的轮廓遮罩（`mask-image`，窗左缘起 aL、往窗里 `WIN_EDGE_SOFT` = 190 个舞台单位线性升到 1）盖着整个轮廓 frame，窗台也在里面；上一轮只给窗台补了 `fo`，左端成了满饱和的方头硬条（完整版 tr 0.25–0.47 带左端最多 −61 级、约 240 px 长；快速版同样）。
  窗台纹理是不透明的，所以用两条叠放的内层条：下层整条（不透明度 `foAl` = fo·aL）、上层带静态 0 → 1 渐变遮罩（`.dfp-hemi--hi`，190 个舞台单位）。叠起来 1 − (1 − b)(1 − u·r) = b + u(1 − b)·r，要等于 fo·(aL + (1 − aL)·r) 需要 u = fo(1 − aL) / (1 − fo·aL)。
  这个商在窗减速到 aL = 1 的几毫秒里会从 1 掉到 0（折线守不住容限），分母改成 √((1 − b)² + 0.006²)（`hemTopAlpha`）：处处光滑，对叠放结果的误差 ≤ 0.3·ε < 0.5/255。上层条的不透明度（`hemTop`）自己不进逐点对拍清单（那几毫秒它掉得陡，但 1 − b ≈ 0，对结果没影响），check-boot 改成对「采样后的下层 + 上层叠起来对 legacy 公式」的误差 < 1/255（三种构型 × 5 个屏幕尺寸实测最坏 0.57 级）。
  实测（对拍帧，窗台第一个紫色像素起 400 px 的亮度，新 − 旧）：由 −61 → −17 级降到逐列 ±10（点状花纹的亚像素抖动，整条窗台一样）；窗台带的平均绝对差 tr 0.25 / 0.30 / 0.34：4.52 / 3.97 / 3.57 → 3.67 / 3.23 / 2.89。
- **窗左缘外的落影（medium）。** 左缘落影条以前按「窗离终态 130 → 45 个单位」淡出，把窗边外的落影交给终态拱窗自己的静态落影；可静态落影在 45 单位（≈ 2.8σ）外几乎还是 0，窗边外有一段没有落影（完整 tr 0.44–0.52 / 快速 0.37–0.41，窗外 20–48 px 比 legacy 亮 8–14 级）。
  现在让位系数 w(d)（d = 终态拱窗左缘 − 窗左缘）取使「窗边处与静态落影合起来恰是 legacy 深度」的值：w = (1 − 2G(d)) / (1 − 0.2G(d))，G 是 σ = 17 的高斯尾（`shadowHandover`、`erfc`）；d = 0 时 0，d ≳ 2.5σ 时 1，单调。实测窗左缘外 20–60 px 的落影剖面与 legacy 差 ≤ 1 级；紧贴窗边的 1–2 个像素还有 ±8 级（边的亚像素位置差，不是落影深度）。
- **窗左缘软边（medium）。** `VEIL_FW_MIN` 16 → 6，`veilOn` 的容限 ×2 → ×3：软边宽度 5–6 个单位（完整版 tr ≈ 0.47、快速版 ≈ 0.40）时薄纱不透明度由 0.27 回到 ≈ 1，窗左缘不再是 1 px 的硬台阶（完整 0.47 下段花海逐像素差 36 级的台阶 → 渐显，最大偏差 ≈ 21 级，因为渐变宽度取 √(fw² + 8²) 比 legacy 宽一点）。
  试过把 `VEIL_FW_SOFT` 8 → 6 / 4（渐变更窄、更贴 legacy）：内层反向缩放 1/s 最大 15 / 22，`veilInv` 的采样守不住 0.005 的容限（0.0053 / 0.0123），没采用。
- **夜品牌标「亮一次」（medium）。** 光晕克隆的满不透明度峰值对应的亮度约为 legacy 的 2 倍（品牌标框内 tr 0.92–1.00 相对终态的平均偏差 4.9–5.4 对 2.6–2.8）；峰值压到 `HALO_PEAK` = 0.55：现在 2.76–2.90（legacy 2.49–2.65）。
- **夜标题光晕层（medium）。** 换成预烘焙叠层那一帧标题框偏暗 1.3 级（光晕区 −3 级），之后一直 −1.9：原 h1 的 filter 是三层 drop-shadow 的**串联**，第三层的紫光（34 px、α .4）是对「字 + 前两层暗影」整块的影子，并列的 text-shadow 只对字形，紫光不够（去掉暗影只回升 0.1，所以不是暗影太强）。

## 已知的边界

- **真窗口里 240 Hz 到不了**：本机集显（Arrow Lake）在转场里要同时画壁纸层、壁纸的遮罩与暗角、玻璃面板的 backdrop-filter 与开屏底板，GPU 成本约 7 ms / 帧，合成器自然落在「每两个刷新一帧」的 120 Hz 档（所有区域都在 120 类，节奏均匀，不再是 60 / 80 / 120 混杂）。
  真窗口消融（`perf-work/realwin/css/*.css`）：去掉玻璃 +27 变化/s、去掉壁纸遮罩 +20、去掉暗纱与颗粒 +13；这三样里前两样属于应用本身的视觉，不是开屏的东西。
- 真窗口（`perf-work/realwin`，屏外真窗口 + WGC 抓屏，3 轮中位数）昼：auto 转场画面真的变化 75.9 → 109.2 次/s（间隔 p95 29.2 → 12.5 ms，> 16.7 ms 的占比 26% → 1.5%），fast 转场 65.4 → 99.6 次/s（p95 37.5 → 12.5 ms，> 16.7 ms 31% → 1.4%），开屏 49.1 → 57.9 次/s；夜不变（auto 转场 142 → 140、fast 115 → 116）。昼转场落在「80 / 120 Hz 类」，到不了 240 的原因见上一条（应用本身的玻璃与壁纸）。
- 离屏测量台（perf-work/harness）里每个出帧间隔 > 8.4 ms 的大头是 `SwapBuffers`（Present）：帧出得越密，离屏纹理的交付越容易背压，旧实现同样有，只是它的帧更稀。别拿它当真窗口的卡顿。
- 昼的开屏（0.1.4 起）锁 120 次/秒：绽开段由画布 + 位图 + 固定渐变的光束承担，不再每拍重光栅；设计、实测与没验证的部分见文末「第六轮」。
- 昼转场 0.7–0.8 s 这一段单帧代价仍有 2.9–3.2 ms（冻结帧基准，第二轮终版；r1 是 4.4 / 4.1），离 4.17 ms 的线余量 1 ms 上下，离屏测量台里 Viz 出帧中位数到了 223–230 fps，但个别轮（偶发长停顿）会掉到 180：剩下的由三块各占一份——控制台条的 BF、
  窗（`.bd-bloom` 的 polygon 遮罩渲染面 + 里面 6–8 层）、窗的落影 + 轮廓 + 底板位图。冻结帧里去掉其中任何一块（窗 −0.9、落影 + 轮廓整组 −1.1、控制台条 −0.6）都让 0.7 s 回到 2 ms 以内；但它们都是看得见的东西，要再降只能改它们的画法（落影 / 轮廓合成更少的层、窗里的静态层预合成一张位图……），都得重新对拍。
- 本机一直有 Claude 桌面端占着 10–14% 的 3D 引擎，Intel 集显上偶发 100 ms 级的单次 Present / CopyOutput 长停顿（LoAF 无脚本归因、`GpuChannel::ExecuteDeferredRequest` 里没有子事件，不是着色器编译：`angle.mjs` 里 0.5 s 之后没有编译任务），位置在 0.7–0.9 s 之间随机；饱和（GPU 线程 > 85% 忙）时才出现，降低占空比是唯一的办法。
- 起步 300 ms 内还有两三个 30–45 ms 的出帧间隔：转场起步时应用侧约 70 个元素同时升成合成层（每个一次小光栅 + 一次 GPU flush），和开屏底板让开后应用第一次被画。后者已被偷看预热消掉大半，前者是应用侧入场（`transition.ts` 的 Entrance）的设计。

## 第六轮（0.1.4）：昼开屏锁 120

用户在 240 Hz 屏上看昼开屏「有些许卡顿」，要求按 120 fps 来做。诊断（0.1.3，离屏集显测量台，day-boot [0, 7 s]）：内容节拍 71 Hz（三组各约 57 Hz，60 fps 封顶），Viz 82 fps，p95 18 ms，> 16.7 ms 占 28%；
解封（每个刷新都推）上不去：绽开段（0–2.7 s）GPU 吃满——每拍写 `.bd-bloom` 的 mask-image 让整屏三层（近景条 / 立绘 / 散花）重新光栅，三条花海条各一个 filter + 遮罩渲染面、`img.bk` 的 blur(60px) 渲染面、
三道光束每拍改 `left` / 渐变 α 重光栅 1900 px 高的旋转层。补丁实测：只去掉蒙版约 99 次/秒，只去掉花海条 / 光晕 / 光束约 81 次/秒，**两组一起去才到 120**。

### 实测的几个坑（都已修，写在这里免得再踩）

1. **`.boot canvas { inset: 0; width: 100%; height: 100% }`** 会盖住后挂的画布的 top / bottom——花海条画布最初跑到了屏幕顶上（对拍平均差 2–7）。`.bd-stripcv` 现在明写 `top: auto; bottom: 0` 并内联 `top: 790px`。
2. **画布缓冲向上取整多出不到 1 px**：整张拿来拉伸 / CSS 宽高写 1600 × 1000 会让内容整体错位最多 1 px（对拍平均差 2.9 → 2.0）。现在 CSS 尺寸 = 缓冲 / 密度，画位图只取内容那一块（源矩形 = 单位 × 密度）。
3. **把光晕位图挂成 `<canvas>`，离屏测量台里 1.8 s 处必有一次 ≈ 500 ms 的 Present 停顿**（只烘不挂就没有；与画布的内容、不透明度、`img.bk` 隐不隐藏、别的画布数量都无关）：改成 `<img>`（PNG blob）挂载后降到 0–1 个、≤ 220 ms（5 轮中位 LoAF 1 个、196 ms；渲染主线程空闲，GPU 线程卡在 SwapBuffers，时刻与应用的 `div.landing-host` 整屏层栅格 / 预热偷看重合，base 的 Present 也有 ≤ 212 ms 的）。原因没查透，没有真窗口数据说明用户会不会看到。**其它挂在 DOM 里的画布（绽开画布、花海条、散花）没有这个现象。**
4. **GPU 画布的 `toBlob` 在主线程上 `ReadbackImagePixels` 等 GPU（一次 69 ms）**：光晕位图用软件画布（`willReadFrequently`）烘，300 × 300 在 CPU 上糊几毫秒。
5. 位图没备好时锁 120 不能提前生效（见 hold）。

## 第七轮（0.1.4 返修）：绽开段的 GPU 活、重播的偷看、测量台 p95 的下限

验收（第六轮）没过的几条里，能在应用侧修的是「GPU 上的活」，不是「测量台的间隔直方图」。这一轮先把两者分开。

### 先量清楚的几件事（都在 `perf-work/` 里有脚本，结论写在这里免得再查）

1. **离屏测量台里 120 的节拍天然 p95 ≈ 9.3–9.7 ms，与应用内容无关。** 对照页 `proto-compositor/cadence.htm`（一个 200 px 的方块，GPU 几乎空闲）：JS 每 2 个 rAF 写一次 → Viz 出帧 119 fps、p95 9.66 ms；WAAPI `steps()` 合成器驱动 → p95 9.28 ms；每个 rAF 一次（240）→ p95 5.1 ms。
   原因：测量台的 BeginFrame 来自离屏窗口自己的定时器，帧时间戳（rAF）恒为 4.17 ms 的整数倍，可 BeginFrame 真正到达渲染进程合成器线程的时刻抖 0.2–2.1 ms（trace 里 rAF 时间戳与 `ProxyMain::BeginMainFrame` 起点之差）；
   每两个刷新一帧时，相邻两次出帧的间隔 = 8.33 + (到达延迟之差)，p95 就落在 9.3–9.8。昼开屏 2.7–7 s 稳态（GPU 空闲、一拍 1.4 ms 的 JS）p95 也是 9.8。**所以「Viz p95 ≤ 9 ms」对任何 120 节拍都达不到，别拿它当应用的指标；有意义的比较是对照页的下限（9.3–9.7）。**
2. **真窗口里 1.25–2.5 s 只有 84–88 次/秒，是抓屏把集显压过了线、调速器升档的结果，不是应用在 240 Hz 上的表现。** 给真窗口记录器加了调速器采样（`realwin/recorder-lite.js` 的 `gov`）：开抓屏时调速器在 1.22 s 因「rAF 间隔 p90 11.9 ms > 1.5 × 刷新间隔」升到 2 档（之后一直到 2.7 s 交班），3 次都是；
   **不开抓屏（`--no-capture`）3 次，整段 0.1–3.0 s 档位恒为 1、没有一次升档，rAF 171 次/秒、p95 7 ms**。用户没有抓屏。今天这台机器的屏幕节拍也只有约 175 Hz（`validate.mjs`：一个空测试页 rAF 170/s、间隔 6.1 ms；10-25 是 240），所以 240 Hz 上的「锁 120」仍没法在真窗口里直接验证。
3. **冷启动 1.8 s 附近那一下 200 ms 级的 LoAF 是一次 GPU 线程上的 `SwapBuffers` 阻塞（渲染主线程只忙 3 ms）**，每次都在 1.78–1.90 s、离屏测量台才有（真窗口 3 轮最长间隔 ≤ 25 ms）；负载越重越长（把光晕位图提成合成层试过：2/2 次 500 ms 以上）。降低 GPU 负载是唯一能影响它的办法——见下面两条。
4. **逐拍的瓦片光栅**：开屏 0.3–1.4 s 每个 tick 有约 4 个 `landing-host` 瓦片光栅（`r2tools/rasterby.mjs` 的按图层汇总：340 个任务 / 900 ms，之后 2–2.8 s 只有 12 个）。罪魁是 `img.bkb`（光晕位图）的不透明度每拍写一次：它不是合成层，每变一次 landing-host 就把那一大块重光栅一遍。试过 `will-change: opacity`：光栅 36 → 6 ms/250 ms 格，但 1.8 s 的 Present 阻塞放大到 500–570 ms（2/2），不能提层。
5. **重播的偷看（`peekApp`）是 90–115 ms 的 LoAF**：重播时开屏下面是设置页（七八块 backdrop-filter 玻璃），偷看让 Viz 把它整个画 5 帧。把偷看关掉：重播 >16.7 ms 占比 0.9% → 0.3%，0.87 s 处的 LoAF 3/3 → 0/3。
6. **重播 0.5–1.5 s GPU 吃满（95–100% 忙、Present 100 ms/格）是「悬崖」**：把绽开画布、前景画布或光束任意一个藏起来，整段立刻回到 30–60%。所以谁都不是「唯一的大头」，而是整体贴着线，每省一点都有用。
